# Rulings — the visual design branch

Every judgement call made while executing
`docs/superpowers/plans/2026-09-02-ledge-visual-design.md`, in the order they
were made. Each says what was decided, why, and what it costs if it turns out
wrong.

Three of them withdraw an earlier ruling of mine — 9 withdraws 8, 22 withdraws
half of 10, and 23 corrects how broadly 7 had been applied. Those are the ones
worth reading first, because each was overturned by evidence rather than by
argument: 9 by a bitmap diff, 22 by reading the pane that had no re-pick
control, 23 by an implementer who was told no and was right.

The ledger they came from was scratch and is gone. This file is what survives,
because a ruling nobody can find at merge time is a ruling nobody made.

Ruling 1: The nine `Theme` colours and the nine badge colours move from an
asset catalog into `Theme.swift` as dynamic `NSColor`s. — This target has no
asset catalog and its project file lists every resource explicitly, so the
plan's "create the catalog" is project-file surgery; worse, a colour name that
fails to resolve does not error at build time, it renders as a placeholder at
runtime, which is exactly the failure nobody on this project can see. Swift
puts the values in the one file the plan already calls the only place a design
number may live, and a typo becomes a compile error. — If wrong, the colours
are harder to preview in Xcode than a catalog would make them.

Ruling 2: Tasks 2 and 3 must register their new files in
`Ledge.xcodeproj/project.pbxproj` by hand — a `PBXFileReference`, a
`PBXBuildFile`, the group membership and the Sources build phase. — The
project has no `PBXFileSystemSynchronizedRootGroup`, so nothing is picked up
automatically, and the plan says nothing about it; an implementer would write
a file the compiler never sees and then chase a confusing failure in the file
that references it. `LedgeCore` is a local SPM package and globs its own
sources, so Task 1 needs none of this. — If wrong, an unnecessary instruction
is followed once.

Ruling 3: Task 4 passes `projectName: nil` at `ShelfView`'s call site when it
adds the property, and Task 5 replaces the literal with the real lookup. —

Ruling 4: The implementer removed a pre-existing `sectionLabel()` extension from
ShelfView.swift, which Task 2 did not authorise. Accepted. — Theme.swift
declares the same name, so this was a hard redeclaration error with no path to a
building commit that kept both. The values differ and the new one is right: the
old extension used 10pt/0.5 tracking, which is the *field* label's metrics from
the design applied to section labels; Theme carries 11pt/0.66 for sections and
10pt/0.5 for fields, correctly separated. The two existing call sites change
appearance, which Task 5 rebuilds anyway. — If wrong, two labels are a point
larger than they were for the length of one commit.

Ruling 5: Theme exports five type modifiers where spec §2 defines seven —
"13 semibold primary" (titles, the empty-state headline) and "12 regular
primary" (field text, sheet rows) have no accessor. The plan's later tasks type
those sizes inline, which breaks the invariant that Theme is the only file
carrying a design number. Task 5 adds `titleText()` and `fieldText()` to Theme
when it first needs them, and Tasks 7 and 8 use them rather than literals. Not
a Task 2 defect — the brief's own code never had them, so this is a gap in the
plan I wrote. — If wrong, two font sizes live in two files instead of one.

Ruling 6: Fix the comment, do not add a guard. — There is nothing to guard
against: the code's behaviour is correct and only its justification is wrong.
Adding code to make a comment true is backwards. Entering the fix loop rather
than deferring, because a false safety claim is exactly what gets a pattern
copied somewhere it is not safe — this project has hit the Turkish case twice
already. — If wrong, one round is spent on a comment.

Ruling 7: `Theme` holds the *shared scale* — the spacing steps, control heights,
radii, type styles and colours the design names. A number describing one view's
own internal geometry, used nowhere else, may live in that view. — The
constraint exists to stop two surfaces drifting apart, and a number with one
call site cannot drift; promoting every literal would turn Theme into a
junk drawer whose members mean nothing. Consistent with the Task 3 review, which
reached the same reading independently. Tasks 5-8 follow it. — If wrong, a later
redesign edits several views instead of one file.

Ruling 7a: The exception is a number that *duplicates* something Theme already
names. The metadata line's `font(.system(size: 11))` restates `rowMeta()`'s size
because the foreground style is conditional; that is a real two-places-to-change.
Left for the task review to weigh rather than pre-judged here.

Ruling 8: Wire the metadata Text through `.rowMeta()` and layer the conditional
tertiary on top; do not drop the helper. — The helper is the design's named
style and Tasks 5-8 need it; deleting it to resolve a duplication would remove
the thing the duplication was of. `foregroundStyle` applied after `rowMeta()`
overrides its default, so the stale case still reads tertiary. Entering the fix
loop rather than deferring: the literal came from the brief I wrote, and leaving
it teaches the next four tasks that typing the number is acceptable. — If wrong,
one round is spent on a font size.

Ruling 9: Ruling 8 was wrong and is withdrawn. `rowMeta()` takes the style as a
parameter defaulting to `.secondary`, rather than the row reversing the chain
order. — Reversing the chain works but leaves the correctness resting on
modifier order, which is exactly the thing that just fooled me; a parameter
makes the failure impossible instead of unlikely. The precedence finding gets a
comment on the helper, because it is measured and the next person will otherwise
repeat it. — If wrong, Theme's helper carries one argument it rarely needs.

Ruling 10: `unavailableFolderBanner` stays a hand-built view rather than an
`ErrorBanner` call, and the two old buttons collapse into the one new action.
Accepted. — `ErrorBanner.message` is a single String and this banner carries two
registers, an amber sentence and a secondary folder list; forcing it through
would have meant either losing the list or inventing a key that merges them.
Removing the stale `Permission…`/`Settings…` keys was forced by `make strings`,
not chosen. — If wrong, two banners in one app are built two ways.

Ruling 11: The PermissionView headline must use `.titleText()`, not the literal
`.font(.system(size: 13, weight: .semibold))` my brief gave it. — That literal
restates what Theme already names, which is the defect class that cost Task 4
two rounds; "the brief said so verbatim" is not a defence when the brief is
mine and wrong. Correctness concern, so it is fixed before review rather than
after. — If wrong, one line reads slightly longer.

Ruling 12: `SettingsLauncher.openWatchedFolders()` gets `@MainActor`. — `NSApp`
is main-actor-isolated and the brief's snippet called it from a nonisolated
static func, which Swift 6 flags twice. The build exits 0 today; the warning is
still describing a real unsafety, and silencing it by ignoring it is how a
future compiler turns this into a stop. Every call site is a SwiftUI button
action, already on the main actor, so the annotation costs nothing. — If wrong,
an annotation is redundant.

Ruling 13: Replace `SettingsLauncher` with `@Environment(\.openSettings)` and
delete the enum. — The deployment target is macOS 14 and `openSettings` exists
there; it is type-checked, it removes the stringly-typed selector, and it makes
the `@MainActor` question moot because the environment action is called from the
view. Strictly smaller and strictly safer than what my brief specified. Entering
the fix loop because a control that silently does nothing is worse than no
control, and this one cannot be caught by a compiler or by any test this project
has. — If wrong, an environment action behaves differently from the selector in
some case neither of us has found, and the footer's SettingsLink is still an
independent route to Settings.

Ruling 14: `TextField(String(), text:)` replaces the brief's `TextField("", …)`.
Accepted. — An empty string *literal* still resolves to the LocalizedStringKey
overload and is extracted as its own catalog key, which fails `make strings`;
passing a `String` value selects the StringProtocol overload with the same
visible behaviour. A real defect in the code I wrote. — If wrong, a placeholder
that was never meant to exist is missing.

Ruling 15: The stale `Extensions` key is removed, one more than the brief's two.
Accepted — it was orphaned by the title becoming empty, and `make strings`
flagged it. — If wrong, a key nothing uses is gone.

Ruling 16: `Add Category` becomes `＋ Add Rule`, in Task 7's fix loop. — The
rubric this task shipped already calls them rules ("Rules apply top to bottom —
the first rule that claims a file wins"), so the button is now the one control
in the pane using the old word, two lines from a sentence using the new one.
Renaming the `Category` *type* is out of scope and stays; this is one label the
spec names twice. — If wrong, the button says "Rule" while the code says
`Category`, which is already true of the rubric.

Ruling 17: Migrate all five to "rule", in Task 7's second fix round. — The spec
started this migration (§8.5 adopted the design's "rule" wording for the rubric)
and stopping halfway is worse than either end state: a user cannot tell whether
the two words name the same thing. Controller checked the blast radius before
ruling: outside this pane the word appears in no user-visible string at all —
the only other hit is `Text(group.category)`, a value rather than the noun — so
the change is five strings in one file. The `Category` type stays; code and UI
already diverged in the rubric, deliberately. — If wrong, five strings say
"rule" while the type says `Category`, which was already true.

Ruling 18: The per-category exclude mechanism is restored. Removing it was not
sanctioned. — The plan's Global Constraints forbid behaviour changes, the spec
is silent on toggles, and absence from a mockup is not a decision to remove a
feature: the boards were drawn without knowing the control existed. The evidence
is decisive rather than a matter of taste — `OrganizePreview.groups`,
`selectedMoves(excluding:)` and `selectedCount(excluding:)` carry 19 assertions
in OrganizePreviewTests, one of them named `excludingACategoryDropsExactlyItsMoves`,
and after this change the app target calls none of them. A restyle that orphans
a tested capability somebody deliberately built is not a restyle. Precedent
also points this way: the one design-implied behaviour change I put to the user
— unclaimed files staying put — they chose to keep today's behaviour.
— If wrong, the sheet keeps a control the design did not draw, which the user
can see and ask me to remove.

Ruling 19: The `Moving…` busy label is restored too. — Same class, smaller: the
brief's static footer snippet dropped it, and a button that gives no sign it is
working during a long batch is a regression the design never asked for.
— If wrong, one label reappears.

Ruling 20: The whole-folder label drops the category name inside a section.
— My composition ruling put the design's flat-list label under a section header
that already names the category, so it now reads "Documents · whole folder"
inside a section headed "Documents". The redundancy is a consequence of my call,
not of the implementer's work, and it flagged it rather than quietly leaving it.
The file case keeps its label: there it shows the *subdivision* folder, which the
header does not repeat. — If wrong, two words are missing from a line nobody has
seen.

Ruling 21: Both are fixed before this ships. — A check that says the opposite of
what it means is worse than no check, and these two sit in the only artefact
that reaches the person who can see the screen. The implementer's report claimed
the Turkish reads naturally and it does; these are meaning inversions rather
than fluency, which is why a fluency read missed them. — If wrong, two sentences
are reworded in a document nobody has followed yet.

Ruling 22: Ruling 10's behaviour half is withdrawn. The banner's action branches
on whether the folder is blocked: blocked → `Open Privacy Settings`
(PrivacySettings.open), merely missing → `Choose Folder Again…` (openSettings).
— My ruling accepted "one destination covers both" without checking what
GeneralPane offers. The reviewer traced it: there is no re-pick control, and
re-selecting the same folder through Add Folder… is a literal no-op, because
`FolderIdentity.adding` dedupes and `AppState.addWatchedFolder`'s guard returns
before `startWatching()` or `refreshFolderStatus()`. So the button opens a
window containing nothing that can fix the fault it sits beside — and it is
reachable only in the state where the full permission screen stays down, which
is exactly when it is the user's only affordance. Worse than Ruling 13's silent
no-op, because this one visibly opens the wrong window. Ruling 10's layout half
— a hand-built banner rather than ErrorBanner — stands. The catalog already
holds `Open Privacy Settings` with its `tr`, so the fix costs no new strings.
— If wrong, a blocked folder offers a route to Privacy & Security that the user
did not need.

Ruling 23: Ruling 7 was applied too broadly and the correction joins the fix
wave. — "A number with one call site cannot drift" is sound; I applied it to
`.font(.system(size: 11, weight: .medium))`, which has three (ShelfView:351,
ShelfView:477, ErrorBanner:39), after the Task 6 implementer flagged it as a
promotion candidate and I said no. Ruling 7a existed to catch precisely that and
fired only on the case already found. Cost: M1-M3, all small, none structural.
— If wrong, one font size lives in Theme that could have stayed in three files.

Ruling 24: T5 joins the fix wave rather than staying deferred. —
`projectName(for:)` takes the first containing project rather than the deepest,
so a project nested inside another's folder labels its rows with the outer
project's name — a wrong destination in the one line whose entire job is naming
the destination. It is one line, it is a pure function, and the reviewer's
framing settles it: a ledger stops being read at merge. — If wrong, a filter and
a max replace a first.

Ruling 25: T7's `index: 0` stays, with a comment. — The branch is unreachable,
but the stakes moved when the index became the user-visible gutter ordinal: a
future caller breaking the invariant would misnumber a card silently rather than
fail. Two lines of comment, not a restructure. — If wrong, a comment describes a
branch nobody reaches.

Ruling 26: `ArrowButtonStyle` keeps its own 0.12/0.22 rather than folding onto
`Theme.Colour.hover` (0.16). Accepted — the values genuinely differ, the fixer
measured rather than assumed, and forcing a fold would change how a control
looks to satisfy a tidiness rule. — If wrong, one style carries two constants
Theme does not name.

Ruling 27: the one residual is accepted as a documentation gap, not a code
defect, and closed in the docs. — The re-review found the fix report's tab-order
narrative wrong in its details: the gutter buttons precede the name field rather
than following it, so "the same tier as the move-up/move-down buttons" was loose
talk. The fix itself is correct — the Button is real, focusable, and its
FocusState both expands the card and lands focus in the field. But the finding's
real content is that nobody has pressed the key: the only account of the
keyboard route came from reading the view tree, and the one part of it that
could be checked was wrong. Check 11 now sends a human to Tab, in both
languages (0ca57a9). — If wrong, two manual-check files carry one sentence more
than they needed.
